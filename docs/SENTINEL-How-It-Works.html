SENTINEL

Driver time-theft detection — how it works, how the data is mapped, and what the fallbacks are

Davis Delivery · operator & engineering reference · generated 2026-06-22 · reflects engine v4.5–4.6

One-paragraph summary. SENTINEL takes three independent records of a driver's day — when they clocked in/out (B600 time clock), when they made deliveries (NuVizz), and where the truck physically went (Motive GPS) — and looks for time that the driver was on the clock but not accounted for by driving or delivering. It compares the real gaps (clock-in → first delivery, last delivery → clock-out, and off-route stops mid-day) against an expected gap (map travel time + a loading/wrap-up allowance). Anything beyond a tolerance is flagged as "unexplained time" and priced in dollars. Everything else on screen is built on top of that one idea.

1. The big picture (data flow)

SENTINEL does not collect raw data itself. Three upstream systems feed a shared Firestore database; SENTINEL reads from it, scores each driver-day, writes one result document per driver per day, and the dashboard reads those results back.

Critical mental model: the raw collections timeclock_daily and nuvizz_rows_raw are owned and populated by external ingestion (the B600 scraper / the NuVizz weekly import that live in MarginIQ, not in this app). SENTINEL only reads them. If a feed stops landing, SENTINEL has nothing to match — and the day will score as "clean / $0" because there is nothing to compute, not because the driver was clean. This is the single most important thing to understand when a dashboard looks empty.

3. How a driver is mapped across systems (identity)

This is the heart of "how everything is mapped." Each system names the same human differently. The employees record is the Rosetta Stone: it carries an externalIds object plus a truck number, and SENTINEL uses those to join the three feeds together.

To match…Match key on the employeeMatched againstNotes
Time clock punchexternalIds.b600timeclock_daily row's display_id / display_name / payroll_idCase-insensitive equality; first match wins.

Truck type (tractor/straight)defaultTruck (truck #)sentinelConfig/truckTypeMap.trucks[truck#]Plus an optional per-driver truckType override.
The #1 real-world failure here: the B600 name and the NuVizz name for the same driver are often different (the schema itself cites "Brent Boyd" vs "Brenton Byrd"). If externalIds.nuvizz doesn't exactly equal the name NuVizz prints, that driver's deliveries never match — you get clock punches with 0 stops, and every day scores "clean / $0." Fixing the driver's externalIds.nuvizz and re-scanning resolves it.

The match-key chain (with fallbacks)

  B600 punch:    externalIds.b600  ->  fullName  ->  "firstName lastName"   (first hit wins)
  NuVizz stops:  externalIds.nuvizz  ->  fullName
  Motive:        externalIds.motive  (no fallback; skipped if absent)
  Truck type:    employees.truckType override  ->  truckTypeMap[defaultTruck]  ->  "unknown"

4. The scan pipeline (per driver, per day)

For each active driver and a given date, the engine runs these steps (_sentinel-scan.js → _sentinel-engine.js):

  1. Resolve identity & truck type from the employees record (§3).
  2. Get the clock punch from timeclock_daily for that date (multi-punch days use the first IN and last OUT).
  3. Get the deliveries from nuvizz_rows_raw for that date, keep only Completed stops that have a parseable "delivery end" time, sort by time.
  4. Window to the shift: drop deliveries before clock-in or after clock-out (those are recorded separately as data-health notes, not scored).
  5. Pick anchors: first on-shift stop = morning anchor, last on-shift stop = afternoon anchor. A single-stop day still anchors both windows (the windows don't overlap, so it isn't double-counted).
  6. Look up travel times yard → first stop and last stop → yard (Distance Matrix, cache first).
  7. Score the morning gap, afternoon gap, and (if Motive ran) the in-route gap; compute risk score, stolen minutes and dollars (§5).
  8. Write one document to sentinelDriverDays/{slug}_{date}.

5. The scoring model

Each scored "gap" is: actual minutes − expected minutes. Expected = map travel time + a human allowance. Whatever exceeds the "ok" tolerance is unexplained.

Gap (flag class)ActualExpectedUnexplained =
Morning (Class 1)clock-in → first deliverytravel(yard→first) + load prepactual − expected, charged above "ok"
Afternoon (Class 2)last delivery → clock-outtravel(last→yard) + wrap upactual − expected, charged above "ok"
In-route (Class 3)off-route minutes between first & last stop (Motive)0 (any off-route is suspect)off-route minutes above "ok"
Data integrity (Class 4)Not a dollar figure — notes like b600_no_punch, nuvizz_no_stops, no_travel_time_to_first.

Pricing the time

Stolen minutes (only the portion above the "ok" floor of each gap) are converted to dollars at an hourly rate that depends on truck type:

Truck typetractorstraightunknown
Default wage ($/hr)27.5023.0025.00

stolenDollars = (stolenMinutes ÷ 60) × wageRate[truckType]. A "self-loader" (load prep ≥ 60 min) is bucketed separately in the reference metrics, since their expected morning gap is much larger.

Why a day can read "clean / $0" without anyone being clean. A morning or afternoon gap is only computed when all three of these exist: a clock punch, a matched delivery anchor, and a travel-time estimate. Miss any one and that gap stays null → contributes 0 → the day falls through to clean. That is correct behavior (don't accuse on no evidence) but it means $0 can mean "no evidence," not "no theft." The dashboard now surfaces this difference explicitly (§9, §10).

9. Baselines (coaching context, not enforcement)

Separately from scoring, SENTINEL computes a per-driver "typical day" (median / P75 / P90 of their own history) and a confidence band based on how many days of data exist. Baselines are display-only context ("worse day than usual") — since v4.5 the fraud judgment is a fixed static threshold the same for every driver, so a driver can't normalize their own theft into an acceptable baseline.

10. Failure modes & how to read them

Because SENTINEL depends on three external feeds, an empty or all-clean dashboard is usually a data problem, not a scoring bug. Use this table to triage.

What you seeWhat it meansWhat to check
Clock times present, 0 stops, $0, "no delivery data"NuVizz feed not matching for that driver/date.Expand the day → "Show all deliveries" → read the diagnostic line (see below).
0 stops and "no clock punch"Neither feed landed — total gap for that day.Coverage probe; nightly scan status.
Whole fleet $0, every median blank, Baselines still populatedRecent raw feed stale (history exists, recent dates don't).Coverage probe — compare newest NuVizz vs timeclock date.
Punch + stops present but still $0Travel-time lookups failing (Distance Matrix / yard address).Confirm SENTINEL_YARD_ADDRESS & GOOGLE_MAPS_API_KEY.

The three diagnostic tools

  1. Coverage probe (fleet-wide): GET /api/sentinel-day-scan?secret=…&coverage=true → returns the newest ingested delivery_date (NuVizz) and date (timeclock). If NuVizz's newest is older than the window you're viewing, the weekly import is the problem.
  2. Nightly job status: the sentinelConfig/nightlyScanStatus doc shows written vs empty vs errors for the last run.
  3. Per-day deliveries diagnostic (per driver): on any day in Investigate, expand it and click "Show all deliveries for this day →". The line at the bottom reports rowsScannedForDate and driverNameMatches:
    • rowsScannedForDate = 0 → no NuVizz rows ingested for that date at all (whole-feed gap → ops/ingestion fix).
    • rows > 0 but driverNameMatches = 0 → the driver's externalIds.nuvizz doesn't match the name NuVizz prints (identity fix → set the correct name, re-scan).

11. Scheduling, endpoints & maintenance

Scheduled jobs

  • Nightly scan — runs daily ~09:00 UTC, targets the date 7 days ago (cushion so the weekly NuVizz email and settled punches have landed). Weekends are skipped explicitly.
  • Weekly baselines — recomputes each driver's "typical day" context.
  • Historical backfill — one-time sweep over the full date range (Motive off for speed).
  • Re-score all — re-applies the current thresholds/config to every stored record without re-fetching raw data (used after you change wages, load-prep, or a driver's truck type).

Security follow-ups (see AUDIT.md). A few items need attention before relying on this deployment: a Firebase API key is committed in source and must be rotated; several endpoints (purge, scan-list delete, introspect) are unauthenticated; and the shared access secret has a hardcoded fallback. These don't affect the scoring math but should be closed out by an engineer.
